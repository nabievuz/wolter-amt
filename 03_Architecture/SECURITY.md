Run/issue ID server tekshiruvi qo‘shimcha signal; token o‘qiladigan bir UID’dagi JWT identity ajratish emas. Hermes’da shell/execute/browser o‘chiq; runtime skill yaratish o‘chiq, memory yozish faqat owner sessiyasida yoki owner typed callback bilan (◇ P-14). **SSH** (faqat Tailscale orqali, Q58; §3.2). `/opt/wolter-amt/current/bin/amt-kill` (`ssh_kill_path`; root:root, immutable release bundle ichida). Owner’ning `amt-kill` uchun alohida sudoers yozuvi bor (`/etc/sudoers.d/70-owner-kill`, F1: aynan shu yo‘l va `kill_cli` argumentlari) — owner umumiy sudo’ni (`80-owner`) olib tashlasa ham kill yo‘li ishlaydi (F1-AT-27). Bayroqlar ([execution-policy.yaml](../09_Config_Templates/execution-policy.yaml) `kill_cli`): `--mode ai_only` yoki `--mode ai_and_ads` (rejim har doim aniq yoziladi; argumentsiz chaqiruv rad etiladi), `--status`, `--self-test` (rejimni o‘zgartirmasdan latch yo‘li, control socket va yuboruvchilar barrier ACK’ini tekshiradi, ◇ P-12). CLI root peer sifatida o‘sha `amt-control` socket’iga boradi va DB, Telegram yoki Paperclip’ni kutmaydi. SSH yo‘li resume bermaydi. Agent yoki builder bu yo‘lni ixtiyoriy sudo orqali ololmaydi.

**Server ham yo‘q.** Owner yoki Ads Manager’da oldindan vakolatli inson managed entity’larni qo‘lda pauza qiladi va cap’ni tekshiradi, owner OpenRouter kalitini o‘chiradi. Bu oflayn mashq mustaqil monitor/responder checklist’ida sinaladi ([KILL_SWITCH](../06_Runbooks/KILL_SWITCH.md)).

### 6.4 Birinchi amal: lokal latch va epoch (◇ P-03)

`amt-control` lokal protected control fayl/journal’ida kill latch va monoton `control_epoch`ni durable fsync qiladi; dispatcher barrier shu paytdan yangi normal write va yangi LLM/media dispatch’ni rad etadi. Snapshot, Paperclip API, Meta yoki Telegram javobi, markaziy DB tranzaksiyasi bu amaldan oldin kutilmaydi. DB ishlamasa latch mustaqil saqlanadi; control storage durable bo‘lmasa servislar fail-closed ishlaydi va OS service-stop/egress containment fallback qo‘llanadi — bu holatda “kill muvaffaqiyatli” deyilmaydi. Startup’da latch yo‘q, o‘qilmaydi yoki DB’ga zid bo‘lsa default-deny; tashqi control manbasi (off-host journal) bilan reconcile qilinmaguncha normal write ochilmaydi.

### 6.5 Keyingi amallar

Har biri mustaqil, timeout va partial natija bilan:

1. **DB mirror va navbat.** `amt_control` funksiyalari orqali `gateway_state.write_mode=killed`; `control_events`ga pre_state (global va pipeline rejimlari, trust darajalari), epoch, audit va outbox. Dispatch intent’i yozilmagan ochiq itemlar (`pending_review`, `pending_approval`, `approved`, `claimed`) → `cancelled`, `reason_code=kill`, reservation bo‘shatiladi. Dispatch intent’i yozilgan yoki `executing` urinish in-flight hisoblanadi va `uncertain → reconciling` orqali remote read bilan yopiladi.
2. **ACK va to‘xtatish.** gateway, executor, llm-proxy, `amt-amo` va ops-bot yangi epoch’ni ACK qiladi; Paperclip agent/routine pauza qilinadi; `amt-workflow` tashqi effektli step’ni dispatch qilmaydi; Hermes billable proxy’dan foydalana olmaydi. Paperclip timeout lokal containment’ni ochmaydi.
3. **Snapshot.** Best-effort account snapshot (`account_snapshots`, `reason=kill_switch`); olinmasa kill hodisasi `snapshot_id=NULL` va sabab bilan davom etadi.
4. **Faqat B.** `amt-control` har managed ierarxiyaning eng yuqori to‘liq managed darajasi uchun executor’ning pause-only yo‘liga so‘rov beradi: status re-read → pause → verify. Per-entity natija `kill_switch_events`ga yoziladi va WF-O02 incident run’iga bog‘lanadi. Faqat pause yoki no-op; activate, budget, creative yoki upload yo‘q.
5. **Tokenlar.** Har agent run’ining gateway/proxy tokenlari revoke yoki rotate qilinadi; normal dispatcher keshlangan permit’larni tashlaydi. Meta credential pause-only yo‘l uchun executor’da qoladi, chunki `protective_pause` `killed`da ham ishlashi kerak. Vendor credential’ni API orqali revoke qilish mumkinligi taxmin qilinmaydi; owner’ning mustaqil vendor login yo‘li sinovdan o‘tadi (§10).
6. **Hisobot.** Natija durable outbox va off-host journal’ga yoziladi: `contained_at`, epoch, in-flight ro‘yxati, A’da davom etayotgan spend, B’da attempted/paused/failed/unverified entity’lar. Biror pauza xato bo‘lsa `partial_failure` — “hammasi pauza” xabari yo‘q (`ALERT_KILLED`). Targetolog yoki owner’ga vendor’da qolganlarni yopish uchun handback boshlanadi (§7).

Lokal barrier vendor bizning fence’ni tekshiradi degani emas. Kill’dan oldin yuborilgan so‘rov keyin bajarilishi mumkin; u vendor read/reconciliation va kerak bo‘lsa pauza bilan yopiladi. Kill javobida lokal containment va remote pause yakunlanish vaqtlari alohida ko‘rsatiladi.

### 6.6 Dispatch barrier va `amt-control` interfeysi

Dispatch barrier gateway UI flag’i emas. Haqiqiy tashqi yuboruvchilar — executor dispatcher, llm-proxy upstream sender, `amt-amo` yozish yo‘li, gateway’ning GitHub chaqiruvi, `amt-eng-proxy` va `amt-release` — har tashqi send boshlanishidan oldin bitta lokal serialization kontraktida amaldagi latch/epoch’ni o‘qiydi; oldindan keshlangan permit bilan yubormaydi. Kill shu chegarada boshlanmagan send’ni to‘sadi; undan oldin boshlangan send in-flight sifatida qayd etiladi. Emergency fallback root egaligidagi fixed service-stop/egress amali bo‘lishi mumkin; servis yoki agentga umumiy sudo yoki ixtiyoriy buyruq berilmaydi.

### 6.7 Containment vaqti va mashq

`ops.kill_targets` (`F3_CONTROLLED_TEST`, accountable owner) uchta qiymatni yopadi: `local_containment_max_ms` — kill qabul qilingandan latch fsync va barcha yuboruvchilarning barrier ACK’igacha; `remote_pause_report_max_s` — B’da har managed entity natijasi (paused/failed/unverified) hisobotigacha; `in_flight_report_max_s` — latch’dan oldin boshlangan send’lar ro‘yxati hisobotigacha. Lokal containment uchun taklif qilingan standart ≤5 s; qiymat owner qarorini kutmoqda (⧗ OD-11). Qiymat tasdiqlanmaguncha UAT-21, UAT-22, F3-AT-25 va F6-AT-08 natijasi `blocked`, PASS emas: chegarasiz “tez ishladi” PASS hisoblanmaydi ([PRODUCTION_ACCEPTANCE](../12_Acceptance/PRODUCTION_ACCEPTANCE.md)).

Mashq: owner belgilagan choraklik to‘liq mashq (technical_operator + owner, owner ishtirokida; `kill_drill` — kunlik 10:00 muddat tekshiruvi: `recovery.full_drill` dalili P75D bo‘lganda owner’ga eslatma, P83D dan har kuni, mashq P92D ichida) — `restore_drill` konteynerida fixture’larda simulyatsiya qilingan Meta endpoint’iga qarshi to‘liq A/B mashqi va production’da Tailscale orqali SSH bilan rejimni o‘zgartirmaydigan `amt-kill --self-test` barrier probe; SSH kill yo‘li faqat shu self-test bilan isbotlanadi, mashq ichidagi kill bilan emas (◇ P-12; [operations.yaml](../09_Config_Templates/operations.yaml) `schedule`). F3-AT-15/25 izolyatsiyalangan race va partial remote holatni, F6-AT-08 HG-F6-03 bilan Step 1 dan oldin to‘liq tartibni tekshiradi. Kill log latch commit vaqti, pre_state, eski/yangi epoch, in-flight dispatch, per-entity natija, outbox yetkazilishi/ACK va resume vakolatini saqlaydi; snapshot vaqti latch’dan oldingi bloklashni almashtirmaydi.

### 6.8 Kill, release va engineering

`killed`da `amt-release` faqat **recovery release** chiqaradi (`non_recovery_release` rad; [release-policy.yaml](../09_Config_Templates/release-policy.yaml) `kill_interaction`, [evolution-policy.yaml](../09_Config_Templates/evolution-policy.yaml) `promotion.kill_interaction`). Recovery release — maqsadi xavfsiz holatni tiklash bo‘lgan release: oldingi tekshirilgan release’ga qaytish yoki kill sababini tuzatuvchi tekshirilgan candidate. U ham mustaqil verification va owner `/release approve` (HG-REL-01) talab qiladi; release global rejimni ochmaydi — buning uchun alohida `/resume` kerak. `release_approvals` `control_epoch`ga bog‘langani uchun kill’dan oldingi har release tasdig‘i bekor bo‘ladi va yangi epoch’da qayta olinadi.

`amt-eng-proxy` latch’ni o‘qiydi va `killed`da engineering LLM dispatch’ni rad etadi. LLM’siz sandbox build va verification tashqi effekt bermaydi, shuning uchun davom etishi mumkin; natija faqat recovery release sifatida chiqadi. Kill/control kodi himoyalangan sirt: o‘zgarishi faqat E sinfi orqali ([evolution-policy.yaml](../09_Config_Templates/evolution-policy.yaml) `protected_surfaces`).

INC-26 PC joyida turgan paytda tamper belgisi bilan boshlansa owner PC’ning tarmog‘ini uzadi va uni production’da yuklamaydi.
2. **ACK.** `privacy_owner` `ops.ack_minutes.critical` ichida ACK qiladi; owner xabardor qilinadi.
3. **Qamrov.** `privacy-policy.yaml` `datasets` bo‘yicha: qaysi dataset va maydon, subyektlar soni bahosi, maqsad, transchegaraviy uzatish va vaqt oralig‘i. Noma’lum qism `unknown` deb yoziladi, nolga tenglashtirilmaydi.
4. **Xabar berish.** Faqat tasdiqlangan `privacy.breach_response` bo‘yicha: qabul qiluvchilar, muddatlar (amaldagi qonun matnidan, sana bilan), shablon va mas’ul. Har yuborish dalili (`sent_at`, qabul qiluvchi, matn revision’i) saqlanadi. Bu hujjat qonuniy muddat yoki regulyatorni kafolat sifatida bermaydi; qabul qiluvchi va muddatlarning huquqiy tekshiruvi — ⧗ OD-16.
5. **Tiklash.** Credential rotation (§10), sessiya va rol revoke, sanitizer regression testi (seeded probe), mustaqil security review. INC-26’da qo‘shimcha — writer fence. Cloudflare hujjatiga ko‘ra tunnel tokeni aylantirilgandan keyin mavjud connector’lar qayta ishga tushguncha ulangan qoladi, shuning uchun owner o‘z qurilmasidan: (1) Tailscale admin konsolida eski AMT tugunini olib tashlaydi; (2) Zero Trust dashboard’da tunnel tokenini aylantiradi ("Rotate token"); (3) "Cloudflare Tunnel Write" huquqli token bilan `DELETE /accounts/<id>/cfd_tunnel/<tunnel_id>/connections` orqali barcha mavjud ulanishlarni uzadi; (4) yangi tokenni faqat yangi hostga qo‘yadi; (5) `GET …/connections` faqat yangi host connector’ini ko‘rsatishini tekshiradi. Keyin: yangi server age kaliti yaratiladi, eski recipient olib tashlanadi va har `secrets/*.sops.yaml` da yangi qiymat yozishdan oldin `sops rotate -i` (sops ≥ 3.9; eskisida `sops -r -i`) — `sops updatekeys` data key’ni almashtirmaydi; bular owner qurilmasida bajariladi, owner private age kaliti AMT PC’ga tushmaydi; builder’ning per-repo deploy key’lari GitHub’da revoke qilinadi va builder’ning Claude Code sessiyasidan owner claude.ai’da chiqadi; `ops.credential_inventory`dagi har credential almashtiriladi, ichki servis sirlari `--rebuild` da qayta yaratiladi; yangi PC `00-owner-bootstrap.sh --rebuild` bilan quriladi (Tailscale’ga yangi bir martalik, oldindan tasdiqlangan auth key bilan, kalit fayldan o‘qilib, to‘liq flag’lar bilan ulanadi). INC-26 tamper belgisi bilan PC joyida turganda boshlangan bo‘lsa, fence va rotatsiyadan keyin owner hal qiladi: o‘sha apparatga yoki yangi apparatga o‘rnatish (tekshiruv va vendor firmware’ini qayta yozishdan keyin); ikkalasida ham ikkala disk tozalanadi va holat `--rebuild` va manbalardan quriladi, tekshirilgan disklardagi ma’lumot production’ga tiklanmaydi, ixtiyoriy forensik nusxa faqat PC ichida ([BACKUP_RESTORE §5.4](../06_Runbooks/BACKUP_RESTORE.md)); tanlov AAR’ga yoziladi. Reklama shu vaqtda provider spending limit va inson Ads Manager custody’sida.
