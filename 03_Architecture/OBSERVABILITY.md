## 5. Mustaqil tashqi monitor

AMT host, ops-bot yoki local Bot API o‘lsa, o‘sha hostdagi bot alert yubora olmaydi. Tashqi heartbeat/dead-man monitor alohida hosting va credential bilan ishlaydi (HG-F2-17: owner monitor xizmati va alternate channel akkauntlarini ochadi va to‘laydi; xarajat `budget.tco`da), faqat health tokeni bilan — biznes, provider yoki approval write kaliti yo‘q. Landing intake hostini ham alohida kuzatadi (`LANDING_INDEPENDENT_HEALTH_TOKEN`). Readiness: `ops.independent_monitor` (`F2_LIVE_INTAKE`: intake/queue failure off-host alert end-to-end) va `ops.independent_monitor_full` (`F6_STEP1`: host, bot va Telegram yo‘qolishi alternate channel bilan).

Minimal heartbeat (`INDEPENDENT_MONITOR_SEND_TOKEN` bilan autentifikatsiya qilinadi): source host/service, nonce (monitor uni HMAC’li ACK ichida aks ettiradi), `observed_at`, oxirgi durable acceptance/delivery/checkpoint vaqti, backlog soni va eng eski yoshi, lokal snapshot yangiligi, active release ACK va control rejimi, sanitizatsiyalangan noma’lum ijro soni, `capi_terminal_before` (avtomatik yuborilishi mumkin bo‘lgan CAPI eventlarining eng erta manba o‘zgarishi va manba sinxron watermark’ining kichigi — host yo‘qolsa [TRACKING_CAPI](TRACKING_CAPI.md) §8 ning 2-qoidasi; `now − capi_terminal_before` 1 soatdan oshsa `ALERT_CAPI_FAILED`) va audit zanjiri boshi (seq va hash; [BACKUP_RESTORE](../06_Runbooks/BACKUP_RESTORE.md) §5.4 forensik solishtiruvi). Monitor har heartbeat’ni saqlagandan keyin ACK qaytaradi va heartbeat tarixini kamida 8 kun saqlaydi (`ops.independent_monitor`); `amt-control` heartbeat’ning DB’dan olinadigan barcha maydonlarini (yuqoridagi vaqtlar, backlog va uning eng eski yoshi, `capi_terminal_before`, audit zanjiri boshi) faqat `amt.heartbeat_snapshot()` (`SECURITY DEFINER`) orqali oladi va har ACK’ni `amt.monitor_acks` ga yozadi; capi-bridge CAPI eventini faqat ACK olgan oxirgi heartbeat’ning `observed_at` vaqtidan beri lease (ikki heartbeat oralig‘i, `operations.yaml#host_loss.capi_dispatch_lease`) o‘tmagan bo‘lsa yuboradi — kechikkan ACK lease’ni uzaytirmaydi; monitor yetmasa eventlar navbatda kutadi (F2-AT-23). O‘chgan monitor o‘z o‘limi haqida xabar bera olmaydi: shu holatni host tomoni aniqlaydi — `amt-control` ACK olgan eng yangi heartbeat yoshi `operations.yaml#host_loss.monitor_unreachable_alert.after` (PT3M) dan oshsa ops-bot orqali `ALERT_MONITOR_UNREACHABLE` beradi (INC-27); ofis internet liniyasi uzilgan bo‘lsa Telegram ham yetmaydi, lekin u holda ishlayotgan monitor o‘zining dead-man alertini alternate kanalda beradi. Customer ID, telefon, raw URL yoki asset metadata tashqi monitorga yuborilmaydi. ## 7. Log, audit va recovery o‘lchovi

Servis JSON log’i journald’da, Caddy sanitized route log’i bilan; boshlang‘ich operational retention 30 kun, auth 90 kun, cost/tracking 24 oy — `privacy.retention`da tasdiqlanadi. Logger token/cookie/authorization/webhook secret/phone/email/IP/fbc/fbp/raw contact va sensitive URL query’ni redact qiladi. `error.stack` va vendor body ham sanitizer’dan o‘tadi. Har event request_id/attempt_id/command revision/config/policy/epoch bilan bog‘lanadi; sirni qidirish regex’dan tashqari seeded probe qiymatlari bilan ham.

Audit chain append’lari serialization lock ostida, parallel commit tartibi aniq; zanjir digest’i off-host bilan solishtiriladi (faqat hash, AMT ma’lumotining nusxasi emas — Q55). Runtime UPDATE/DELETE yo‘q. Lokal kill DB’siz journal’ga yoziladi, keyin auditga idempotent import qilinadi. “Audit bor” tashqi side effect aynan bir marta bo‘lganini isbotlamaydi; remote attempt dalili kerak.

**RPO va lokal snapshot yangiligi.** RPO — ma’lumot yo‘qotish oynasi: eng yangi **foydalanish mumkin bo‘lgan** lokal snapshot’ning (uning `amt` dump’i tugagan va `MANIFEST`i tekshiruvdan o‘tgan) consistency nuqtasidan mantiqiy xatogacha bo‘lgan vaqt ([operations.yaml](../09_Config_Templates/operations.yaml) `rpo_definition`). Lokal snapshot (har kecha 02:00 Asia/Tashkent va har upgrade oldidan, o‘sha RAID1’da, shifrlanmagan, 7 kun; Q54, Q55) faqat **mantiqiy xato**dan — noto‘g‘ri migration, o‘chirish, noto‘g‘ri ommaviy yozuv — himoya qiladi; RPO shu holat uchun o‘lchanadi. Host yo‘qolishi RPO bilan qoplanmaydi: PC buzilsa disklar boshqa PC’ga ko‘chiriladi, ikkala disk yo‘qolsa AMT tarixi yo‘qoladi — qabul qilingan risk; intake va CAPI landing va amoCRM’dan qayta quriladi (Q55; [TRACKING_CAPI](TRACKING_CAPI.md) §8). Qiymatlar faqat `recovery.intake_datasets`, `recovery.full_datasets` va `workflow.recovery`da, soniyada; NFR-07/I14 dagi umumiy RPO≤24h — mantiqiy xato uchun yuqori chegara. Consistency nuqtasi — 02:00 dagi run’da `amt` dump’ining boshlanishi, shuning uchun ketma-ket tungi nuqtalar orasi 24 soat va har tungi run tugasa oyna 24 soatdan kam qoladi; xato yoki o‘tkazib yuborilgan run `ALERT_BACKUP_STALE` va bitta catch-up run’ni boshlaydi, uzaygan oyna hisobotda ko‘rsatiladi, yashirilmaydi. Approved dataset RPO 24 soatdan qisqa bo‘lsa qo‘shimcha lokal snapshot yoki WAL/PITR yo‘li (shu RAID1’da) gate oldidan quriladi ([BACKUP_RESTORE](../06_Runbooks/BACKUP_RESTORE.md)).

Snapshot stale qoidasi (`backup_stale_alert_rule`): jadvaldan olingan kutilgan run muddati (02:00 + kutilgan run davomiyligi + zaxira) o‘tsa yoki bo‘sh joy yetmagani uchun run o‘tkazib yuborilsa darhol `ALERT_BACKUP_STALE` va bitta catch-up run. Alert ochiq turganda ma’lumot yo‘qotish oynasi 24 soatdan oshishi mumkin — bu hisobotda ko‘rsatiladi, yashirilmaydi. Snapshot muvaffaqiyati exit code bilan emas, `MANIFEST` (har artefakt sha256 va boshlanish/tugash vaqti, engine/schema/code/config revision’lari, consistency nuqtasi) tekshiruvi bilan tasdiqlanadi; restore drill xatosi `ALERT_RESTORE_FAILED`. Snapshot o‘sha host va o‘sha RAID1’da (Q55): root kompromati yoki ikkala diskning yo‘qolishi snapshot’ni ham yo‘q qiladi [X]; owner qarori bo‘yicha alohida nusxa yo‘q, bu qabul qilingan risk.

Restore drill avariya va oxirgi tiklangan event vaqtidan dataset RPO’ni o‘lchaydi. Avariya→biznes qaytishi va recovery start→biznes qaytishi alohida; yangi PC yoki disk ko‘chirish, kalit (age qog‘oz/QR nusxasi, Q56), tunnel va Tailscale qadamlari va operator kutish yashirilmaydi (`business_recovery_clock_includes_host_keys_tunnel_rebuild: true`). Zaxira PC yo‘q (Q55), shuning uchun host yo‘qolishidagi biznes tiklanish vaqti qismlar yig‘indisi, har qism `measured` yoki `estimated` deb belgilanadi: F0 o‘rnatish va bootstrap vaqti `build` rejimida haqiqiy PC’da — yangi PC yo‘lining eng yaqin o‘lchangan proksisi (`--rebuild` farqi — owner bajaradigan [BACKUP_RESTORE](../06_Runbooks/BACKUP_RESTORE.md) §5.1 skriptlari, deploy key’ni qayta qo‘shish, `git verify-tag` — ixtiyoriy mashq bajarilgan bo‘lsa o‘lchanadi, aks holda taxmin qilinadi va dalilda `estimated` deb belgilanadi (`host_loss_time_seconds.rebuild_delta.method`)), kalit, tunnel va Tailscale qadamlari — o‘lchangan yoki tabletop’da taxmin qilingan (`keys_tunnel.method`) (haqiqiy rotatsiya production’ni buzadigan joyda — sinov resurslarida yoki tabletop) va `restore_drill` da staged eksportdan o‘lchangan qayta qurish vaqti va amoCRM tarixini rate limit’li API orqali o‘qish vaqti — u hisoblanadi (`source_fetch`, `estimated`); bu end-to-end mashq emas va shunday yoziladi. Process crash, disk ko‘chirish va host-loss kafolatlari ajratiladi. Read/ingest → remote reconciliation → consent-valid CAPI → tracking/owner resume tartibida biznes tiklangan payt qayd etiladi. UAT-21–25/29 shu dalillarni talab qiladi.
