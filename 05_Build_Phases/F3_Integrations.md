## 1. Gateway va dispatcher

Role identity process/credential chegarasi bilan; allowlist `approval-policy.yaml`. Agentlar faqat gateway, LLM faqat proxy orqali. `amt-gateway` policy admission, `amt-executor` dispatch, `amt-control` kill epoch va rejimlar, `amt-quota` lokal kvota; qolgan servislar o‘z DB grantida. Agentga raw SQL, connector yoki provider kaliti yo‘q. Reviewer writer process/credential’ini ko‘rmaydi.

Write proposal immutable payload + asset hash + offer/review/policy/role revision’lari + control epoch bilan yoziladi. `new → pending_review` faqat action’da `review_required: true` bo‘lsa ([approval-policy.yaml](../09_Config_Templates/approval-policy.yaml) `actions`); aks holda `pending_approval`. Creative/ad uchun mustaqil Reviewer pass **majburiy** va aniq revision’ga bog‘langan; Reviewer subyektni faqat `review.get_subject` orqali o‘qiydi va verdict faqat unga berilgan `subject_hash` uchun qabul qilinadi (◇ P-20). Policy talab qilgan inson approval’i qo‘shimcha alohida shart: inson approval’i Reviewer fail/missing/stale holatini chetlab o‘tmaydi va Reviewer pass inson approval’ini almashtirmaydi. Approval qarorlari: `approve | reject | edit_decrease | expire`; tahrir faqat raqamni kamaytiradi va yangi revision yaratadi.

Command holatlari ([execution-policy.yaml](../09_Config_Templates/execution-policy.yaml)): `pending_review → pending_approval → approved → claimed → executing → succeeded`; noaniq remote javob `uncertain → reconciling → succeeded | failed_confirmed | manual_resolution`; `rejected`, `expired`, `cancelled` alohida; `failed_confirmed` tashqi ta’sir bo‘lmaganini isbotlaydi; `approved → awaiting_manual → done_manual` owner qo‘lda bajaradigan actionlar uchun. Qo‘shimcha o‘tishlar: `claimed → cancelled` (dispatch intent’dan oldin kill yoki revoke; reservation bo‘shatiladi), `approved|claimed → cancelled` (guard xatosi, `reason_code` bilan), `awaiting_manual → expired`, `manual_resolution → succeeded|failed_confirmed` (operator dalili bilan), shadow item TTL’da `expired`. Kill sababi `cancelled` + `reason_code=kill`.

Atomic claim/lease lokal parallel dispatch’ni to‘sadi; tashqi API idempotency kafolati taxmin qilinmaydi. Har dispatch/retry/rollback oldidan expiry/freshness/role/offer/asset/review/policy/epoch qayta tekshiriladi. Policy mismatch eski approval’ni yaroqsiz qiladi. Lokal privileged barrier kill bilan normal dispatch’ni tartiblaydi. Vendor’ga ketgan request keyin tugashi mumkin: attempt in-flight qayd etiladi, noaniq natija read/reconcile qilinadi, zarur compensating action yangi approval bilan. Timeout’ni failed deb qayta execute qilish taqiqlanadi. Command + audit + notification outbox bitta durable tranzaksiya. Workflow step’lari command’larga `step_command_links` orqali bog‘lanadi; run holati command holatini almashtirmaydi (EVO-AT01/EVO-AT02 ning F3 qismi isolated).

## 3. Pul, fleet va business guardrail

**Reklama cap’i.** Pul integer minor unit + valyuta. Paid Meta cap USD 1 500/oy (150 000 USD minor, `ads.monthly_cap_minor`). Native akkaunt valyutasi/timezone, cumulative counter, verified MTD va pending commitment reconcile qilinadi.

- **Provider spending limit majburiy va AI’dan mustaqil (Q37 ✅).** HG-F3-02 da owner Ads Manager account spending limit’ni `cap_update_formula` bo‘yicha qo‘yadi (◇ P-02); `vendor.meta_cap` faqat API read-back kutilgan qiymatga teng bo‘lsa PASS. Har oy 1-kuni HG-OPS-01. Uni olib tashlash yoki almashtirish faqat yangi owner Q bilan (⟲ Q37), readiness qiymati bilan emas (`ads.provider_spend_limit_required: true`).
- **Admission:** `verified_MTD + Σ(active_daily × remaining_days) + Σ(held commitments) + requested ≤ ads.monthly_cap_minor − ads.safety_margin_minor`, provider counter valyutasiga `ads.fx_policy` bilan o‘tkaziladi ([budgets.yaml](../09_Config_Templates/budgets.yaml) `admission_rule`, `commitment_basis`). Reservation `rejected/expired/cancelled` da bo‘shatiladi, `succeeded` da settle qilinadi. Oy boshida to‘liq cap ko‘r-ko‘rona qayta qo‘shilmaydi.
- **`protective_pause` — qo‘shimcha deterministik qatlam, provider limit o‘rnini bosmaydi (◇ P-21).** Spend pacer tekshiruvi har sync siklida `amt-sync` da; trigger (headroom ≤ safety margin yoki spend ma’lumoti `budget.ads_pacing` cutoff’idan eski) bo‘lsa `amt-control` `protective_pause` command beradi, `amt-executor` pause-only yo‘li re-read → pause → verify → `protective_actions` → ALERT_PROTECTIVE_PAUSE. Faqat managed entity, faqat pause; activate, budget oshirish yoki create hech qachon. `killed` va `read_only` rejimda ham ishlaydi. Inson boshqaradigan (foreign) kampaniyalar AMT tomonidan pauza qilinmaydi: ular cap’ni yesa urgent alert va owner handback.
- **Rolling 24h:** har entity uchun oddiy budget harakatlari **mutlaq qiymatlarining yig‘indisi** ishonchli oyna boshi bazasining ≤20% i (◇ P-01); +20% va −20% birga 40% hisoblanadi. Inson tahriri drift signalini yopmaydi; noma’lum yoki nol baza — owner review va oshirish blok. CBO/ABO bir marta sanaladi.
- **KC-02 biznes natija guard’i:** KC-02 ishlagan yoki lead→contract `data_status` `valid` bo‘lmagan paytda budget oshirish blok.

**Fleet.** `serviceable = rented + reserved + available`; `total = serviceable + maintenance` (I10). Ritm `operations.yaml#schedule` dan (◇ P-06; ⧗ OD-14): 08:00 so‘rov, 09:00 eslatma, `fleet_snapshot_accepted` hodisasida rent tahlili, 09:45 batch cutoff, 14:00 eskalatsiya. Rent takliflari faqat bugungi qabul qilingan snapshot revision’idan; 09:45 dan keyin kelgan snapshot bo‘yicha rent bandi o‘z TTL’i bilan alohida item. 14:00 gacha valid snapshot bo‘lmasa shu kun barcha oddiy rent budget o‘zgarishlari (kamaytirish ham) hold; himoya nazoratlari ta’sirlanmaydi. Eskirgan snapshot hech qachon valid emas. Sale increase `sale.readiness` talab qiladi (gate F6_STEP2, ◇ P-09).

**Tracking.** Bir kun fail — alert; ikki ketma-ket kun — `read_only`; stale/missing freshness guard risk oshirishni alohida bloklaydi.

**AI runtime cap.** USD 150/oy (15 000 USD minor); proxy va gateway media admission actual+reserved atomik. cost-watchdog: ulush 80% da alert, 100% da agent pauzasi; kalit `key_noncritical_stop_pct` (90%) da muhim bo‘lmagan yangi admission to‘xtaydi (`proxy_admission_pause`); hard admission keyingi timer’ga qoldirilmaydi. Langfuse ikkilamchi reconciliation; u bo‘lmasa local ledger va provider cap qoladi, ishonchli hisob bo‘lmasa yangi billable dispatch blok. Billing reconciliation `billing_unreliable_noncritical_pause_after_hours` (★ 6 soat) dan uzoq ishlamasa muhim bo‘lmagan agentlar pauza qilinadi va reconciliation isbotlangach avtomatik qaytadi. Watchdog, ulush yoki oy chegarasi bilan pauza qilingan agent faqat owner `agent_resume` (typed code, `never_auto`) bilan qayta yoqiladi.

## 4. Operatsiya, kill va human handback

**Sync va kill criteria.** Sync Meta insights/Umami/cost, webhook/intake reconciliation, data freshness va deterministik kill criteria. `kill_criteria` job dushanba 07:30 (KC-01, KC-02), `exposure_guard` har sync siklida ([kill-criteria.yaml](../09_Config_Templates/kill-criteria.yaml), `operations.yaml#schedule`). Past N, yetilmagan kogorta va zero-qualified exposure qoidalari business readiness’dan va kanonik `data_status` jadvalidan o‘qiladi. KC-01 trigger’i (`kill_criteria_l0`): pipeline `L0_shadow` + urgent alert + human handback + funnel-analyst’ga C05 RCA issue. Handback ACK `handback_acks` da, entity release va epoch ledger’da. Faqat xabar yuborish biznes boshqaruvi qabul qilindi degani emas. KC-01 dan keyin pipeline C05 RCA, owner `takeover_scope_change` (HG-F6-04 qaytadan) va owner `pipeline_mode_change` ikki bosqichli L1 ga o‘tkazmaguncha L0 da qoladi.

**Kill.** Birinchi amal — **lokal durable latch va epoch** (◇ P-03): yangi normal write va LLM/media dispatch yopiladi; snapshot, Paperclip pause yoki remote Meta javobi bundan oldin kutilmaydi. Standart rejim A (AI to‘xtaydi, reklama mustaqil cap ostida davom etishi mumkin). B = A + har managed entity’ning **eng yuqori to‘liq managed darajasi** pauza (campaign to‘liq managed bo‘lsa campaign, aks holda ad set yoki ad); foreign parent’ga tegilmaydi. Writer sinflari [SECURITY §6](../03_Architecture/SECURITY.md) jadvalida: `killed` da amoCRM, GitHub, LLM va media yozuvlari rad; CAPI, landing CRM yetkazish, bildirishnoma va ACK davom etadi; `amt-release` recovery bo‘lmagan release’ni rad etadi; `protective_pause` ruxsat. Partial failure va in-flight reconcile ochiq ko‘rsatiladi; token/kalit tozalash bu yo‘lni yarim qoldirmaydi. Kill maqsad vaqtlari `ops.kill_targets` da (`local_containment_max_ms`, `remote_pause_report_max_s`, `in_flight_report_max_s`; lokal containment uchun ≤5 s taklif — ⧗ OD-11) va F3-AT-25 da o‘lchanadi. SSH kill yo‘li `/opt/wolter-amt/current/bin/amt-kill` (root:root; owner’ning `amt-kill` uchun alohida sudoers yozuvi (`70-owner-kill`) bor — umumiy sudo olib tashlansa ham ishlaydi); Telegram kill DB va ops inbox’ni talab qiladi — ular ishlamasa darhol SSH. Kill owner-only; deputy incident ACK huquqi kill huquqi emas (⧗ OD-04). Resume: global kill’dan keyin har pipeline `min(oldingi, L1_approve_each)`, global `shadow` saqlanadi, `read_only` sababi hal bo‘lmaguncha qoladi; released entity owner qayta takeover’isiz ochilmaydi. [KILL_SWITCH](../06_Runbooks/KILL_SWITCH.md).

**Egress, rollar va ops-bot.** Egress per-UID default-deny; gateway va proxy o‘z socket’lari bilan; Hermes Telegram uchun tekshirilgan endpoint set. Root fixed runner ixtiyoriy buyruq qabul qilmaydi. Bir UID’dagi token spoofing qoldiq risk deb yopilmaydi. Rollar runtime DB’da (`amt.people`, `amt.roles`, `person_flags`); eksport PR’i eski DB holatini bosmaydi. HG-F3-05 da owner har odamni `/role add` bilan qo‘shadi; flag’lar `/role flag add|remove <tg_id> <flag> [expires]`, effective flag faqat valid membership bilan; `cloud_password_attested_at` bo‘lmasa approval tugmalari va tg-auth rad; tugashdan 7 kun oldin REMINDER_ROLE_EXPIRY; har `role_change` off-host monitor kanaliga ko‘zgulanadi; asosiy guruh a’zoligi drift’i ALERT_ACCESS_DRIFT (◇ P-10). Ops-bot approvals/outbox, `[Qabul qildim]` ACK, fleet wizard, kontent, rollar va mustaqil monitor bilan ishlaydi; owner buyruqlari (`/mode`, `/takeover`, `/graduate`, `/resume`, `/budget raise`, `/role …`, `/asset clear|revoke`, `/release approve`, `/proposal approve`, `/work`, `/decisions`) typed code bilan — bu ataylab qilingan amal tasdig‘i, ikkinchi autentifikatsiya omili emas.
