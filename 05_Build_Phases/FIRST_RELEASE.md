# First F1 release — one-time owner trust initialization

Status: specification · Runtime: NOT_RUN · Decision: Q65 (2026-10-25).

Read this before the first F1 AMT-host publication, when ops-bot cannot yet record a Telegram approval. Canonical controls and full service/ACK mapping are `release-policy.yaml#initial_release` and `#deployment`; the manifest shape is `schemas/candidate-manifest.schema.json`. Existing-server admission and all unmet human gates still apply. This procedure installs no ad, paid LLM/media or agent capability.

1. **Prepare unprivileged artifacts.** Build/test once as `amt-build` from owner-merged `main`; record hashes and redacted F1 evidence. Prepare a manifest with `deployment.kind: initial`, `phase: F1`, the complete F1 service floor and its derived ACK set, `base_release_id: null`, empty `capabilities_enabled` and empty snapshot capabilities. Completion: the closed schema and semantic phase/service checks pass; tests remain `not_run` until actually executed.
2. **Owner establishes the root of trust.** Through Tailscale SSH, the owner verifies the pinned fixed installer, signer file, owner-signed annotated release tag, main reachability and exact manifest commit/artifact digests. The installer has fixed operations only; repository scripts, dependency hooks and caller-selected commands never run as root. Initialize the minimum DB schema and the existing one-time owner/break-glass role seed. Completion: owner identity and installer provenance are recorded; no runtime service or working tree can replace them.
3. **Check initial admission.** Refuse an existing current/active release, prior release ledger, killed latch or already-bound bootstrap belonging to another attempt. Initial publication is not restore/rebuild or kill resume. Initialize control to `shadow`, both pipelines `L0_shadow`, admissions denied only when no prior state exists. Completion: the trusted initializer proves absence and the fail-closed initial state without overwriting an existing latch.
4. **Owner approves the exact initial candidate offline.** The fixed helper prepares the canonical envelope defined in `initial_release.approval_envelope`; the owner signs it with an approved release signer. Verify host/bootstrap identity, signer-to-owner binding, full manifest and nullable approval bindings, nonce, epoch, revisions and expiry. A one-shot fixed transaction records `typed_confirmations`, `release_approvals`, audit and singleton bootstrap identity together. Completion: exactly one candidate/nonce/approval/activation identity is bound; partial transaction or changed replay is refused. The SSH signature is the Q65 approval source, not a fabricated Telegram session.
5. **Publish through the ordinary publisher.** `amt-release` rechecks the durable approval row **and** signed release tag, all bindings and the effective ACK set. Candidate services read the explicit staged immutable path with admissions denied. Every deployed ACK-class service must ACK its exact revision; none-ACK services still prove health/version. Completion: only a complete matching ACK set publishes `current` atomically and seals bootstrap. No F2/F3 absent service is awaited during F1; no deployed protective service is exempt.
6. **Handle first failure without bypass.** There is no previous current release: leave current absent and admissions denied. Retry only the same pending candidate/approval/nonce/activation identity, with original expiry and all checks. Do not seed another approval or change the manifest. An expired or irreparable initial attempt stops for an explicit owner recovery decision. Completion: recovery evidence distinguishes actual ACKs from missing ones; runtime is never reported live from a tag, seed or attempted activation alone.
7. **Close the one-time path.** Preserve bootstrap/audit evidence and demonstrate the next `deployment.kind: update` through normal ops-bot `/release approve <candidate_id>` typed approval plus an owner-signed tag; its nonnull base must equal active current. The offline importer is permanently sealed for new approvals. Readiness capability enablement remains a later independently approved release/transition. Completion: normal Telegram release approval works and an offline second seed is refused.

Acceptance extends F1-AT-24 and the first-release H03 probes: valid initial path; wrong signer/host/nonce/hash/role/policy/epoch/expiry; missing tag or DB row; replay/change; existing state or killed latch; nonempty initial capabilities; omitted phase/protective service; forged/extra/duplicate ACK; failed first ACK retains no current and exact identity; normal update requires active base and Telegram approval. All actual server evidence is produced during F1, not during document preparation.
