## A. Sale/rent landing va qabul

`wolter-landing` alohida Next.js/TypeScript strict repo, `go.wolter.uz` production Dokploy. Ikkala oqim to‘liq quriladi. `content/variants/*.json` schema’da variant/pipeline/offer/CTA/media/active bor; kontent koddan ajratilgan. `content/offers.snapshot.json` owner tasdiqlagan `offers.yaml` revision’idan CI orqali generatsiya qilinadi (HG-F2-15, `offers.initial`); CRO narx yoki da’voni erkin tahrirlamaydi. Tasdiqlangan offer bo‘lmasa landing jonli trafikka chiqmaydi — placeholder narx yoki da’vo qo‘yilmaydi. Landing’dagi har media asset huquqi tozalangan bo‘ladi (`offers.asset_rights`; `asset_rights_clear`, yuklagan odam o‘zi tozalamaydi). Immutable asset hash va offer revision landing build’iga bog‘lanadi. Mobile performance boshlang‘ich ≥85 mezoni F2’da o‘lchanib kalibrlanadi (★).

1. Capture: first/last UTM, `ad_id`, variant/offer revision, ruxsat bo‘lsa fbc/fbp, client-generated submission ID va server event ID. Cookie retention va marketing matni owner tasdiqlagan policy bo‘yicha. PII input maskalanadi.
2. Server validation, abuse/rate limit va honeypot; telefon formati tekshiriladi. **`accepted` javobi faqat shifrlangan durable custody tranzaksiyasi commit bo‘lgach.** Commit bo‘lmasa forma muvaffaqiyat ko‘rsatmaydi; foydalanuvchi saqlangan submission ID bilan xavfsiz qayta yuboradi. Google Sheet yo‘q.
3. Holat: `accepted → crm_pending → crm_confirmed`; remote timeout `uncertain`, qo‘lda ko‘rib chiqish `needs_review`. CRM credential faqat landing servisining server tomonida. Contact + lead yaratish va CRM lookup bosqichlari ledger’da; client resend, worker parallelizmi va crash biznes idempotency bilan boshqariladi. Tashqi API’da aynan bir marta kafolati taxmin qilinmaydi; noaniq remote natija tekshirilmasdan qayta create qilinmaydi.
4. Custody’dagi shifrlangan payload agent warehouse’ida emas. AMT yetkazish holatini pull bilan oladi: landing PR’i faqat o‘qish uchun `GET /internal/delivery?since=<cursor>` endpoint’ini qo‘shadi (javob PII’siz; token hash’i landing env’ida, HG-F2-13), sync-worker uni `SYNC_LANDING_DELIVERY_TOKEN` bilan o‘qiydi ([ARCHITECTURE §6.1](../03_Architecture/ARCHITECTURE.md)). Warehouse’da faqat custody reference, event ID’lar va sanitized agregat. Accepted→CRM backlog, tasdiq yo‘qligi, `uncertain`/`needs_review` uchun alohida reconciliation va javobgar bor; CRM outage va Pixel’siz consent holatlarida ham bu signal ishlaydi.
5. Xizmat roziligi va marketing maqsadi ajratilgan (`privacy.purposes`, HG-F2-07); matn lead ma’lumotini ko‘radigan qabul qiluvchilarni nomlaydi — `privacy-policy.yaml#off_host_flows`: Cloudflare edge (TLS shu yerda tugaydi), amoCRM, Meta CAPI (◇ P-76). Marketing roziligi bo‘lmasa ham xizmat murojaati CRM’da yuradi; marketing Pixel/CAPI/Clarity yuborilmaydi. Purpose, policy version, vaqt/manba va withdrawal saqlanadi. Hash shaxsiy ma’lumotni anonim qilmaydi. Withdrawal retry/backfill oldidan tekshiriladi. 6. Umami (`stats.wolter.uz`) tasdiqlangan cookiesiz rejimda; Clarity va Pixel faqat tegishli consent’dan keyin. Lead browser va server bir event ID bilan dedup; ID client retry’da ko‘paymaydi. Qualification biznes ta’rifi bilan, marketing event eligibility esa consent bilan ajratiladi.

Builder faqat PR tayyorlaydi; merge va deploy owner’da (HG-F2-01, Q46.4 ✅); landing env qiymatlari HG-F2-13; Umami HG-F2-02/11. Landing va Umami release yo‘li — owner Dokploy deploy’i (`amt-release` emas, uning AMT host’dan tashqari credentiali yo‘q). Production env, backup target va restore operatori production Dokploy hosti uchun HG-F2-18 da aniq ko‘rsatiladi.

**Published deployment evidence (WF-B04 S09).** F2 landing build’i `GET https://go.wolter.uz/.well-known/amt-deployment.json` da PII/secret’siz static metadata chiqaradi; hozirgi hujjatlarda boshqa deployment metadata route belgilanmagan. Yopiq javob maydonlari: `schema_version: 1`, `landing_merge_commit` (40 lowercase hex), `build_digest` (`sha256:<64 hex>`), `content_artifact_hashes` va `tracking_artifact_hashes` (build’ga kirgan tegishli fayllarning sorted relative path → SHA-256 xaritalari), `offer_snapshot_hash` (aynan generated snapshot bytes’ining SHA-256’i). Xaritalar fayl kontentini oshkor qilmaydi. `build_digest` metadata faylining o‘zini chiqarib tashlagan, sorted path+byte-hash inventory bilan belgilangan deploy artefakt digest’i; self-reference yo‘q. CI metadata’ni aynan landing merge commit’dan avtomatik yasaydi; qo‘lda metadata qiymatini yozish yoki metadata’ni ilovadan alohida deploy qilish build xatosi. Butun tuple expected build evidence sifatida merge-commit CI artefaktidan olinadi; sahifadan o‘qilgan qiymat o‘zini o‘zi tasdiqlamaydi. Offer-only o‘zgarishda ham owner deploy qiladigan landing merge commit va uning generated snapshot build’i shu tuple bilan bog‘lanadi; faqat AMT config commit’i yetmaydi.

Owner shu exact landing artefaktini Dokploy’da deploy qiladi. `sync-worker` faqat yuqoridagi same-origin HTTPS GET’ni bajaradi (JSON ≤64 KiB, unknown/missing field rad, `Cache-Control: no-store`; redirect boshqa hostga kuzatilmaydi). Kuzatilgan **barcha** tuple maydonlari expected qiymatlarga teng bo‘lgandagina `landing_snapshot_matched`; bir xil offer hash, CI pass, merge yoki owner “deploy qildim” xabari alohida o‘zi deployment dalili emas. 404, timeout, stale/mixed tuple yoki mismatch → ACK yo‘q, S08/S09 ochiq, S06 dependent dispatch yopiq va operatorga eskalatsiya; oldingi ishonchli revision saqlanadi. Qabul WF-TEST-B04-E2E/MISSING/UNCERTAIN’da: tracking-only va content-only release’da offer hash o‘zgarmasa ham old landing commit/build rad, to‘liq mos yangi tuple qabul; metadata va app bir artefaktda ekanligi build dalili bilan tekshiriladi. Bu read-only tekshiruv yangi write capability yoki agent privilege bermaydi; owner merge/deploy gate’i saqlanadi.

## E. Tracking hard gate

Holat mashinasi [tracking-health.yaml](../09_Config_Templates/tracking-health.yaml) da; tekshiruvlar va `check_id` ro‘yxati [TRACKING_CAPI §6](../03_Architecture/TRACKING_CAPI.md) da.

2. **Real lead dalili:** kamida bir real lead klik → durable accepted → CRM confirmed → qualified → consent-valid CAPI zanjiri bilan dalillanadi (`real_lead_e2e_evidence`); test event real kuzatuv o‘rnini bosmaydi.
3. **≥14 kun report_only.** Soat HG-F2-09 ro‘yxatidagi barcha faol ad’lar `go.wolter.uz`ga yo‘naltirilgan paytdan boshlanadi (ad’lar qisman ko‘chirilsa soat boshlanmaydi). Haqiqiy hajm, consent denominatorlari va missingness yig‘iladi.
4. Har gate check uchun formula, denominator, oyna, min_sample, `warn`/`fail` chegaralari data asosida owner PR bilan tasdiqlanadi (`tracking.thresholds`, HG-GIT-01); `warn` qoidasi ⧗ OD-17, read_only’dan chiqish N’i ham shu kalitda (◇ P-18). Noma’lum chegaraga default taxmin berilmaydi.
5. Keyin **7 ketma-ket kun barcha gate check’lari `pass`** (`tracking.pass_7d`): fbc/fbp, untagged leads, CAPI error/dedup, Pixel–CRM, accepted vs CRM receipt, queue age va sync freshness. Streak’ni faqat `pass` davom ettiradi; `fail`, `unknown`, `stale`, `low_n` uni uzadi; `not_applicable` faqat owner tasdiqlagan check uchun. No-consent lid Pixel–CRM missing deb soxta failure qilinmaydi.
6. HG-F2-08 owner revision bilan PASS (F2_TRACKING_PASS). Bu active health/freshness o‘rnini bosadigan abadiy bayroq emas. HG-F2-08 dan oldin premortem qayta ko‘riladi ([PREMORTEM](../00_Decisions/PREMORTEM.md)).

Go-live’dan keyin: bir kun fail — alert; ikki ketma-ket fail kun — global `read_only` (`tracking_read_only` himoya nazorati). `read_only`dan chiqish: `tracking.thresholds` dagi N ketma-ket `pass` kuni va owner `/resume` (◇ P-18). **Missing/stale data alohida guard orqali risk oshiruvchi dispatch’ni darhol bloklaydi.** F2 kuzatuvda bo‘lganda F3/F4 build va isolated test davom etadi; F5 real shadow HG-F2-08 ni kutadi.
