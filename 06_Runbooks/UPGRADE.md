## 1. Prepare va isolated sinov

1. Change PR muammo → kutilgan xulq, exact pinned version, source commit, image digest, litsenziya, security advisory, data/config/schema mosligi va tegishli eval matritsasini beradi. `infra/VERSIONS.lock.md` yangilanadi; `latest` deploy manbai emas. Proposal’da majburiy **acceptance plan**: texnik mezon, biznes guardrail, baseline va measurement revision, minimal sample/maturity, maksimal kuzatuv, stop/hold/rollback triggerlari (`evolution.outcome_policy`).
2. **Bir marta build (`build_once_promote`):** artefaktlar sandbox’da unprivileged `amt-build`/`amt-sandbox` ostida bir marta quriladi; digest’lar candidate manifest’ga yoziladi; verification aynan shu digest’larda; `amt-release` aynan shu digest’larni publish qiladi. Merge fast-forward yoki rebase, tree-hash tengligi bilan; teng bo‘lmasa yangi manifest va qayta verification.
3. **Lokal pre-upgrade snapshot majburiy:** **har** upgrade’dan oldin — OS yoki paket, vendor komponent (`cloudflared`, `tailscale`, PostgreSQL, Langfuse, Paperclip va boshqalar), kod yoki config release — `amt-backup --pre-upgrade` (`operations.yaml#local_snapshot.pre_upgrade_run`). Snapshot o‘z katalogida (`/var/backups/amt/<YYYY-MM-DDTHHMMZ>-pre-upgrade`), tungi snapshot bilan bir xil tartib va tarkibda: avval `amt` dump’i (uning boshlanishi — consistency point), keyin `paperclip`, Langfuse ClickHouse → MinIO → Langfuse PostgreSQL, keyin fayllar ([BACKUP_RESTORE §2](BACKUP_RESTORE.md)); `MANIFEST` sha256 tekshirilmaguncha upgrade boshlanmaydi. Avtomatik xavfsizlik yangilanishlari (`unattended-upgrades`) uchun o‘sha kechaning 02:00 snapshot’i xizmat qiladi: `apt-daily-upgrade.timer` drop-in’ida avval `OnCalendar=` (bo‘sh — standart 06:00 ni o‘chiradi), keyin `OnCalendar=*-*-* 03:30:00 Asia/Tashkent`, `RandomizedDelaySec=0`, `Persistent=false` (o‘tkazib yuborilgan kecha boot’da bajarilmaydi), shuning uchun ular 03:30 da — snapshot’dan keyin va 04:30 dagi `restore_check` muddat tekshiruvidan oldin — ishlaydi (`systemctl list-timers` bilan tekshiriladi) va snapshot tugab tekshirilmagan kechada o‘tkazib yuboriladi — tekshiruv `apt-daily-upgrade.service.d/10-amt-snapshot.conf` dagi `ExecCondition=` (bu `[Service]` sozlamasi, timer drop-in’ida e’tiborsiz qoladi); har o‘tkazib yuborish jurnalga yoziladi, ketma-ket ikkinchisi `ALERT_BACKUP_STALE` (`operations.yaml#local_snapshot.automatic_security_updates`). Restore nuqtasi code/config/schema digest’iga bog‘lanadi; production rollback — shu snapshot’dan restore (§4). **Rollback testi F6 Step 1 oldidan** va har destruktiv migration oldidan shart.
4. Staging restore live credential, job va remote write egress’isiz; start `killed` (◇ P-16). Staging ishga tushishidan oldin egress tekshiriladi: konteyner ichidan allowlist’dagi test endpoint’ga ulanish o‘tadi, allowlist’da yo‘q manzil (masalan `openrouter.ai` yoki `<subdomain>.amocrm.ru`) rad etiladi; `graph.facebook.com` (CAPI test event’lari) va Telegram diapazonlari (staging boti) faqat test credential’lari bilan ishlatiladi; `iptables -S DOCKER-USER` da `ve-amt-staging` qoidalari bor ([environments.yaml](../09_Config_Templates/environments.yaml) `staging.runtime`). Resurslar [environments.yaml](../09_Config_Templates/environments.yaml) dagi staging/sandbox yozuvlaridan; prod bilan kesishma yo‘q. Paperclip’ning eski process va run’lari to‘liq to‘xtatiladi; clone faol job’ni qayta yubormaydi. Sanitizatsiyalangan data, o‘z test sirlari va sintetik remote’lar; production DB nomi yoki drop skripti ishlatilmaydi.
5. Migration, immutable config/schema validatsiyasi va faol servis ACK; smoke va tegishli hard/regression eval. Model yoki adapter o‘zgarsa — har rol uchun haqiqiy tool-use va identity; qamrov mos bo‘lsa golden til testi. Xavfsizlik nazorati pasaytirilmaydi.
6. **Schema-aware rollback sinovi:** eski code + mos config va eski schema snapshot/PITR yoki tasdiqlangan forward repair. Yangi schema ustiga eski binary qo‘yish rollback emas. Migrationdan keyingi accepted lead/attempt/outbox/billing saqlanishi va remote reconciliation rejasi isbotlanadi; RPO/RTO target va o‘lchangan qiymat yoziladi.

## 2. Review, release va production tartibi

**Ilk F1, ops-botdan oldin (Q65):** [FIRST_RELEASE](../05_Build_Phases/FIRST_RELEASE.md) bir martalik trust initialization yo‘li. Owner fixed SSH installer/importer signed exact candidate envelope’ini tekshirib typed confirmation, canonical release approval, audit va singleton initialization marker’ni atomik yozadi. Existing current/prior history/killed state yoki boshqa bootstrap rad; manifest initial/F1/null base va bo‘sh capability’larda. Oddiy publisher approval DB yozuvi VA signed owner tag/readiness/ACK tekshiruvlarini baribir bajaradi. Birinchi ACK failure’da current yo‘q va admission denied; faqat aynan pending candidate/nonce/approval/activation qayta tekshiriladi. Yangi seed, boshqa candidate yoki expiry extension yo‘q. Ushbu yo‘l keyingi update/restore uchun approval bermaydi. Dastlabki baseline review’i Q66 `evolution-policy.yaml#initial_build_review`da; engineering E human review talabi saqlanadi.

**Keyingi update tartibi:**

1. Owner PR’ni merge qiladi (HG-GIT-01).
2. Owner release tasdig‘i — yozuv, tag nomi emas: ops-bot `/release approve <candidate_id>` (typed code; `upgrade_release`; HG-REL-01) `release_approvals` yozuvini yaratadi: `manifest_digest`, `verification_id`, verdict, `evaluator_revision`, `policy_revision`, `role_revision`, `control_epoch`, approver person_id, `nonce_hash`, `approved_at`, `expires_at`.
3. Owner imzolagan annotated `release-*` tag. GitHub tag ruleset: `release-*` va `F*-done` ni yaratish/o‘zgartirish/o‘chirish faqat owner, bypass yo‘q. Publisher imzoni `/etc/amt/release-signers` bo‘yicha, commit `main`dan yetib borilishini va tag commit = manifest commit ekanini tekshiradi. Engineering credential’lari faqat `cand/*` ga push qiladi; builder tokeni `release-*` yarata olmaydi.
4. `amt-release` (root fixed entrypoint) `validate → prepare → activate → ack`: aynan manifest digest’lari; update manifest base’i active current’ga teng; `deployment.services/required_acks` to‘liq installed inventar, cumulative phase floor va capability dependency’lari bilan `release-policy.yaml#deployment`dan qayta tekshiriladi. Required ACK aynan deployed ACK-class servislar, none-ACK servislar health/version bilan; full kataloglar o‘zgarmaydi. Future-phase absent servis kutilmaydi, installed protective servis yashirilmaydi. ACK yetishmasa oldingi release saqlanadi. Config bundle ham shu `validate → prepare → activate → ack` yo‘lidan o‘tadi; ACK mismatch eski active’ni saqlaydi va tegishli dispatch’ni bloklaydi. Rollar YAML’dan qayta yuklanmaydi (`roles_reload: never_reseed_runtime_DB`). Muhim policy/rol/offer/model o‘zgarishi pending approval’larni revalidate yoki invalidate qiladi.
5. Read-only smoke → reconcile → `operational_validity` va tracking/freshness tekshiruvi (gate emas; `readiness.yaml#rules.gate_time`) → maintenance hold `maintenance_release` bilan yechiladi → kuzatuv.

FE_RELEASE profili yopilishidan oldin ham kod va config xuddi shu root fixed publisher, `release_approvals` yozuvi (verification maydonlari bo‘sh bo‘lishi mumkin) va owner imzolagan `release-*` tag bilan chiqadi; FE yozuvni verification natijasiga bog‘laydi.

**Kill bilan munosabat (`release_classes`):** `normal` — har qanday owner tasdiqlagan release, global rejim `killed` bo‘lsa rad etiladi. `recovery` — manifest’i `release_class: recovery` deb e’lon qilgan va faqat containment, reconciliation yoki oldin tekshirilgan release’ni tiklaydigan owner tasdiqlagan release; `killed` paytida ham ruxsat.

**Maintenance hold** (`execution-policy.yaml#maintenance_hold`): release paytida `global_mode: read_only`, `proxy_admission: paused`; tugagach `restore_previous_modes_on_release: true` — `maintenance_release` faqat hold o‘zgartirgan o‘lchovlarni tiklaydi, L2 pasaytirilmaydi; oyna ichida yoqilgan kill yoki protective control o‘z chiqish qoidasigacha qoladi. Bu kill emas (`is_kill: false`); invoker `amt-release`; owner mavjud bo‘lishi shart. Oyna ichida incident yoki rollback bo‘lsa kill/resume qoidalari ([KILL_SWITCH §4](KILL_SWITCH.md)).

**Oyna:** 14:00–18:00 Asia/Tashkent, dushanba emas ★ (`operations.yaml` `upgrade_window`). Sabab: dushanba 07:30 kill-criteria va 08:00–09:00 haftalik hisobot; 14:00 dan oldin 10:00 change set va ertalabki fleet ritmi. Tasdiqlangan kritik security tuzatishi oynadan tashqarida ham chiqishi mumkin — xuddi shu qadamlar, qamrov va dalil bilan.

**Builder huquqi:** build/test unprivileged `amt-build` user’da; builder sudo’si F1 qabulidan keyin buyruq allowlist’iga toraytiriladi va F6 Step 1 dan oldin to‘liq olinadi (HG-F6-06: guvoh + credential rotatsiyasi; ◇ P-05). Agentda root/sudo yo‘q. Keyin tizim paketi yoki compose yangilanishi — owner SSH (Tailscale) orqali yoki HG-OPS-02 (aniq buyruq allowlist’i, muddat, owner revoke); undan keyin F6-AT-11 va F1-AT-19 qayta PASS. Doimiy keng sudo qaytmaydi.

**Kuzatuv:** umumiy 24 soatlik oyna yo‘q. Oyna, scope va stop qoidalari o‘zgarish sinfi bo‘yicha `release.scope_observation`da; natija `evolution.outcome_policy` bo‘yicha. `observed` ≠ `business_accepted`; infra/security o‘zgarishi uchun texnik qabul + biznes zarari yo‘qligi guardrail’i, `business_accepted` esa sabab bilan `not_applicable`.

## 4. Production failure va rollback

Primary ACK → qamrov bo‘yicha safe latch/hold → owner qarori. Noto‘g‘ri release yoki config’ni immutable eski bundle’ga qaytarish yetarli bo‘lsa schema mosligi tekshiriladi. DB restore kerak bo‘lsa — upgrade oldidan olingan lokal snapshot’dan ([BACKUP_RESTORE §8.3](BACKUP_RESTORE.md)), [BACKUP_RESTORE §5](BACKUP_RESTORE.md) dagi locked ketma-ketlik bilan: start `killed` → read/ingest → remote reconciliation → consent-valid backfill → tracking va restore shartlari (`execution-policy.yaml#restore.preconditions`; gate emas) → owner resume (`control_resume`). Backupdan keyingi vendor write’lari snapshot bilan “bekor” bo‘lmaydi; in-flight `uncertain` attempt’lar reconcile qilinadi, tasdiqlangan compensating command alohida.

Harness rollback: eski controller oddiy davom etmaydi (epoch fence). Mos kod bilan yangi epoch yoki forward repair; eski kod o‘qiy olmaydigan holatdagi run’lar to‘xtatilib (`blocked`) WF-E02 disposition’ini kutadi va [RUN_RESUME](RUN_RESUME.md) orqali `manual_resolution`ga o‘tadi.

Credential yoki izolyatsiyani zaiflashtirib xizmatni live yoqish yo‘q. Proxy/model ishlamasa to‘g‘ridan-to‘g‘ri provider yoki fallback engine ochilmaydi. Qisman rollback, yo‘qolgan data yoki RTO’dan oshish — ochiq insident; 48 soat ichida AAR va tegishli test/ADR/SOP o‘zgarishi. Resume `min(oldingi, L1)`, eski shadow/L0 saqlanadi; muddati o‘tgan approval yoki released entity tirilmaydi.

### 4.1 Release controller ishlamasa — owner qo‘lda root tiklash

`amt-release`ning o‘zi himoyalangan sirt; uni amaldagi (eski) controller publish qiladi. U ishlamasa:

1. Owner SSH (Tailscale) yoki ofisdagi lokal konsol bilan kiradi; kill latch (`amt-kill --status`) holatiga tegilmaydi.
2. Oldingi tasdiqlangan release katalogi `/opt/wolter-amt/releases/<release_id>` ning digest’i uning manifest’i va `release_approvals` yozuvi bilan solishtiriladi; mos kelmasa davom etilmaydi.
3. `current` symlink root sifatida atomik ravishda oldingi release’ga qaytariladi; ta’sirlangan unitlar qayta ishga tushiriladi va servis ACK’lari tekshiriladi.
4. Qo‘lda amal audit’ga yoziladi va insident ochiladi (INC-23); tasdiqlanmagan kod hech qachon shu yo‘l bilan chiqarilmaydi, builder ishtirok etmaydi.
