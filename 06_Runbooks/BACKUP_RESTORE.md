**RPO ta’rifi:** ma’lumot yo‘qotish oynasi — mantiqiy xato vaqtigacha mavjud bo‘lgan eng yangi **yaroqli** lokal snapshot consistency point’idan xatogacha bo‘lgan vaqt (`operations.yaml#rpo_definition`). Host yo‘qolishi alohida Q55 doirasida.

Umumiy mantiqiy-xato talabi **RPO ≤24 soat** saqlanadi; faqat kunlik 02:00 jadval bu talabni kafolatlamaydi. Alert/catch-up eskirishni ko‘rsatadi, RPO bajarilganini isbotlamaydi.

F2 intake va F6 to‘liq dataset qabulidan oldin har dataset uchun tasdiqlangan target (soniya), maksimal consistency-point oralig‘i, completion/scheduling chegarasi, qamrab olinadigan xato-run stsenariylari, detection/catch-up muddati va o‘lchangan eng yomon usable-point yoshi `recovery.*_datasets` daliliga yoziladi. Kunlik jadval — hozircha baseline: target uchun yetarli zaxirali qisqaroq consistent snapshot intervali yoki WAL/PITR **shu RAID1’da**, Q55 bo‘yicha offsite nusxasiz, rejalashtiriladi va izolyatsiyalangan drill’da tekshiriladi. Tanlangan interval jadval va timerga birgalikda kiritiladi; readiness tasdiqlanmaguncha profil `pending`, target oshirilmaydi va guard yumshatilmaydi. Har run/tekshiruvda `now - newest_usable_consistency_point` o‘lchanadi; target buzilsa dalilda breach va `ALERT_BACKUP_STALE`, ochiq blocker qayd qilinadi. Dataset RPO/RTO qiymatlari uchun yagona manba `recovery.*` readiness (`rpo_rto_source`); yangi SLA bu hujjatda belgilanmaydi.

### 2.1 Qamrov chegarasi

Lokal snapshot faqat mantiqiy xatodan himoya qiladi: buzilgan migration, o‘chirish, noto‘g‘ri bulk write. U shu RAID1’da turadi, shuning uchun host kompromati, ikkala diskning yo‘qolishi yoki o‘g‘irlanishi snapshot’larni ham yo‘q qiladi yoki ochib qo‘yadi [X]. Bu owner qabul qilgan xavf (Q55): AMT tarixi — approval, audit, readiness imzolari va ledger’lar — yo‘qoladi; lead’lar landing store (production Dokploy) va amoCRM’da saqlanadi; CAPI eventlari shu manbalardan qayta yaratiladi, lekin qayta yuborish dedup’ga tayanmaydi: Meta bir manbali eventlarni (faqat server yoki faqat brauzer) dedup qilmasligini va bir xil ma’lumotli ikki ketma-ket server eventidan birortasini ham tashlamasligini aytadi, `QualifiedLead` va `Contract` esa faqat server eventlari. Shuning uchun faqat yo‘qolgan host yubora olmagan eventlar qayta yuboriladi; qolganlari — oxirgi yaxshi heartbeat’dagi `capi_terminal_before` dan oldingi (yo‘qolishdan oldin avtomatik yuborish yo‘lidan chiqqan) va holati noma’lum eventlar — `skipped_unknown_prior_send` bo‘ladi (§5.1, 7-qadam). Cloud VM’da tiklash, alohida mashq hosti va zaxira PC yo‘q (Q55). Bitta disk nosozligidan RAID1 himoya qiladi; PC nosozligida disklar boshqa PC’ga ko‘chiriladi (§5).

## 3. Tekshiruv va drill vaqti

Jadval yagona: [operations.yaml](../09_Config_Templates/operations.yaml) `schedule`:

- `backup` — har kuni 02:00, `amt-backup.timer` (systemd).
- `restore_check` — kunlik 04:30 muddat tekshiruvi (WF-O03; 03:30 dagi avtomatik xavfsizlik yangilanishlaridan keyin): `recovery.restore_check` dalili P25D yoshga yetganda `restore_test` muhitiga izolyatsiyalangan DB restore (§8.1) — taxminan oylik, doim P30D ichida va qabul uchun vaqt qoladi.
- `kill_drill` — kunlik 10:00 muddat tekshiruvi (WF-O03, ◇ P-12): `recovery.full_drill` dalili P75D yoshga yetganda ops-bot owner’ga eslatadi, P83D dan har kuni; owner choraklik to‘liq mashqni (owner ishtirokida) P92D ichida belgilaydi.

`restore_drill` — jadval nomi emas, faqat muhit nomi: choraklik to‘liq mashq bo‘ladigan izolyatsiyalangan konteyner ([environments.yaml](../09_Config_Templates/environments.yaml), §4). `restore_test` — faqat DB tekshiruvi uchun alohida baza.

- **Har snapshotdan keyin:** snapshot yoshi, hajmi, exit status, `MANIFEST` sha256 (har artefakt) va qolgan bo‘sh joy.
- **Stale qoidasi:** jadvaldan olingan run deadline’i (baseline: 02:00 + kutilgan run davomiyligi + margin) o‘tsa, run joy yetmagani uchun o‘tkazib yuborilsa yoki usable-point yoshi tasdiqlangan targetdan oshsa darhol `ALERT_BACKUP_STALE` va bitta catch-up run (`…-catchup` katalogi); bu RPO breach’ini yopmaydi. Target/eng yomon o‘lchov va failed/missed run’lar hisobotda ko‘rinadi (`backup_stale_alert_rule`, `rpo_definition`). Run davomiyligi va margin F1’da o‘lchanadi; interval/PITR tanlovi §1 bo‘yicha qabul qilinadi.
- **Har upgrade oldidan** (OS yoki paket, vendor komponent, kod yoki config release): `amt-backup --pre-upgrade`; `MANIFEST` tekshirilmaguncha upgrade boshlanmaydi ([UPGRADE §1](UPGRADE.md)). Avtomatik xavfsizlik yangilanishlarini o‘sha kechaning tekshirilgan 02:00 snapshot’i qoplaydi; u bo‘lmasa yangilanish o‘tkazib yuboriladi.
- **Restore tekshiruvi (`restore_check`, taxminan oylik ★):** oxirgi tekshirilgan snapshot `MANIFEST` sha256 qayta tekshiruvi va `restore_test` ga izolyatsiyalangan DB restore (§8.1); natija `build/ops/restore-checks.md`.
- **Choraklik (owner belgilaydi) va katta migration oldidan:** AMT PC’dagi izolyatsiyalangan `restore_drill` konteynerida to‘liq mashq (§4) — lokal snapshot’dan restore, PII’siz manba eksportidan qayta qurish (host-loss stsenariysi; CAPI qayta yuborish konteyner ichidagi sintetik endpoint’ga), fixture’larda simulyatsiya qilingan Meta endpoint’iga qarshi kill A/B, schema-aware rollback; keyin production’da owner Tailscale orqali SSH bilan `sudo /opt/wolter-amt/current/bin/amt-kill --self-test` (rejim o‘zgarmaydi, ◇ P-12).
- **Gate’lar:** intake custody, Umami va CRM uzilishidan tiklash **HG-F2-14 oldidan** (`recovery.intake_drill`, F2-AT-21; landing custody va Umami restore — production Dokploy hostidagi izolyatsiyalangan restore target’ga (owner, HG-F2-18); jonli DB ustiga hech qachon). To‘liq mashq **HG-F6-03 va F6 Step 1 oldidan** (`recovery.full_drill`, gate paytida dalil 92 kundan (`P92D`) eski emas; F6-AT-08, F6-AT-09, F6-AT-10), `restore_drill` konteynerida.

Drill dalili: snapshot ID va vaqti, ma’lumot yo‘qotish oynasi (§1 ta’rifi bo‘yicha o‘lchangan RPO), restore start → validated vaqti, target vs o‘lchangan RPO/RTO, stsenariy (mantiqiy xato, disk ko‘chirish yoki host yo‘qolishi), yetishmagan artefakt, tashqi egress nol isboti, production `control_epoch` va kill latch’ining mashqdan oldin va keyin bir xilligi, CAPI eventlarining uch soni — qayta yuborilgan va `skipped_unknown_prior_send` ning ikki sababi, `terminal_before_loss` va `unknown_state` (§5.1, 7-qadam) — va responder ACK. Maqsadga yetmasa PASS yo‘q — `ALERT_RESTORE_FAILED`, blocker egasi va sanasi bilan.

**Host yo‘qolishi vaqti.** Zaxira PC yo‘q (Q55), shuning uchun host yo‘qolishidagi biznes tiklash vaqti end-to-end mashq bilan o‘lchanmaydi — u **komponentlar yig‘indisi**, har komponent `measured` yoki `estimated` deb belgilanadi: (1) F0 o‘rnatish va bootstrap vaqti `build` rejimida haqiqiy PC’da — yangi PC yo‘lining eng yaqin o‘lchangan proksisi; `--rebuild` farqi (owner bajaradigan §5.1 skriptlari, deploy key’larni qayta qo‘shish, `git verify-tag`) — ixtiyoriy mashq bajarilgan bo‘lsa o‘lchanadi, aks holda taxmin qilinadi va dalilda `estimated` deb belgilanadi (`host_loss_time_seconds.rebuild_delta.method`); (2) kalit, tunnel va Tailscale qadamlari — o‘lchangan yoki tabletop’da taxmin qilingan (`keys_tunnel.method`) — writer fence (§5), `sops rotate` (§8.4), Tailscale qayta autentifikatsiyasi (§7.1); real rotatsiya production’ni buzadigan joyda bir martalik sinov resurslarida yoki tabletop bilan; (3) `restore_drill` da staged eksportdan o‘lchangan qayta qurish vaqti va amoCRM tarixini rate limit’li API orqali o‘qish vaqti — u hisoblanadi (`source_fetch`, `estimated`). Hisobotda bu end-to-end mashq emasligi ochiq yoziladi. Tavsiya (ixtiyoriy, owner hal qiladi): F2 live intake’dan oldin, PC’da hali production ma’lumoti yo‘qligida, haqiqiy PC’da bir marta owner bajaradigan `--rebuild` va §5.1 mashqi — shunda `--rebuild` farqi taxmin emas, o‘lchangan qiymat bo‘ladi. F6 Step 1 mezoni o‘zgarmaydi: yig‘indi `recovery.full_datasets` dagi tasdiqlangan host-loss target ichida bo‘lishi shart, aks holda Step 1 blocker ([F6_GoLive](../05_Build_Phases/F6_GoLive.md) Step 0A).

Konteyner ichidagi sintetik endpoint’lar bilan uzilish va replay testi: CAPI qayta yuborish sintetik Meta endpoint’iga, host-loss qoidasi bilan (§5.1, 7-qadam) — uch son (qayta yuborilgan, `terminal_before_loss`, `unknown_state`) yoziladi; sintetik endpoint Meta dedup’ini isbotlamaydi va bunday da’vo qilinmaydi; kill A/B poygalari fixture’larda, simulyatsiya qilingan Meta endpoint’iga qarshi ([KILL_SWITCH §6](KILL_SWITCH.md)); live entity activation yoki production CRM status o‘zgarishi yo‘q. SSH kill yo‘li mashq ichida kill bilan sinalmaydi — uni faqat production’da owner Tailscale orqali SSH bilan bajargan `sudo /opt/wolter-amt/current/bin/amt-kill --self-test` isbotlaydi (rejim o‘zgarmaydi, ◇ P-12). Owner tasdiqlagan PAUSED Meta test integratsiyasi (F6-AT-08 (2)) production’da global `shadow` rejimida, F3-AT-05 dagi `origin=test` PAUSED-fixture istisnosi bo‘yicha (production credential’lari, faqat PAUSED test entity, activation simulyatsiya qilinadi; faqat B kill ishlatadigan pauza chaqiruvi `origin=test` item orqali sinaladi, production kill bajarilmaydi — production `control_epoch` va kill latch o‘zgarmaydi) Step 1 dan oldin bajariladi — hech qachon `staging` yoki `restore_drill` da emas.

**Writer fence** (`host_loss` `writer_fence`). Yangi yoki qayta o‘rnatilgan host ishga tushishidan oldin eski host yozuvchi sifatida to‘xtatiladi — ikki faol writer qolmaydi. ### 5.1 `--rebuild` dan keyingi root qadamlar (yangi PC, stsenariy (d))

Har qadam boshlanish va tugash vaqti bilan AAR’ga yoziladi (host-loss vaqti — §3).

1. **Insident va fence.** O‘g‘irlik yoki ruxsatsiz jismoniy kirish bo‘lsa — avval INC-26: breach javobi (`privacy.breach_response`, ⧗ OD-16) va `ops.credential_inventory` dagi har credential rotatsiyasi (§7); belgi topilganda PC joyida bo‘lsa, u tarmoqdan uzilgan qoladi va production’da yuklanmaydi (stsenariy (e)). Writer fence’ning 1–3-qadamlari (§5) yangi PC ishga tushishidan oldin; 4–5-qadamlari quyidagi 3- va 5-qadamlarda.

CAPI ledger disklar bilan yo‘qolgan, qayta yuborish esa dedup’ga tayanmaydi: Meta bir manbali eventlarni (faqat server yoki faqat brauzer) dedup qilmasligini va bir xil ma’lumotli ikki ketma-ket server eventidan birortasini ham tashlamasligini aytadi, `QualifiedLead` va `Contract` esa faqat server eventlari. Oynadan eski event — `skipped_too_old`. Uch son — qayta yuborilgan, `terminal_before_loss` va `unknown_state` — dalilga yoziladi (F6-AT-09, UAT-23); dalil ikki marta sanash yo‘qligini isbotlaydi deb da’vo qilmaydi — u faqat qoidalar qo‘llanganini ko‘rsatadi.

### 5.3 Qayta ochish ketma-ketligi

1. **Read/ingest:** tekshirilgan lokal snapshot’dan (a) yoki manbalardan (d) core DB, config va kalitlar; inbound durable capture va zarur read-only sync. Normal write va LLM/media dispatch hali yopiq. Original event ID va vaqti saqlanadi. Servislar bosqichma-bosqich yoqiladi (platforma va auth → intake/CAPI/sync → gateway/executor), har bosqichda servis ACK.
2. **Remote reconciliation:** snapshotdan (yoki uzilish boshlanganidan) keyingi CRM/Meta o‘zgarishlari, in-flight/`uncertain` attempt’lar, accepted submission’lar, pending billing, provider cap va MTD, rol/policy/offer revision’lari solishtiriladi. Tashqi success’dan keyin crash bo‘lgan attempt ko‘r-ko‘rona qayta dispatch qilinmaydi. Inson tahriri drift’i yangi baseline deb yashirilmaydi.
3. **Backfill:** host yo‘q paytdagi amoCRM status o‘zgarishlari `events` API (`lead_status_changed`) orqali qayta o‘qiladi; landing’dagi `submission_delivery` WF-B01 run’lariga dedup bilan qo‘shiladi. Original event vaqti, pinned vendor yosh sharti (`vendor.meta_capi`: maksimal yosh — Meta’ning 7 kunlik oynasi), joriy consent va withdrawal tekshiriladi. Yuborilgani noma’lum event dedup’ga tayanib qayta yuborilmaydi: host yo‘qolishida §5.1 7-qadamdagi uch qoida ishlaydi (yo‘qolgan host yubora olmagan event qayta yuboriladi; `capi_terminal_before` dan oldingisi va qolgani audit bilan `skipped_unknown_prior_send`); ledger saqlangan holatda `uncertain` attempt [TRACKING_CAPI §5.3](../03_Architecture/TRACKING_CAPI.md) qoidasi bilan reconcile qilinadi. Juda eski event audit bilan skip qilinadi, yangi sana bilan jo‘natilmaydi. CRM intake reconciliation CAPI’dan mustaqil.
4. **Restore shartlari** (`execution-policy.yaml#restore.preconditions`; bu gate emas, `max_evidence_age` qayta qo‘llanmaydi): live read health, tracking/freshness va mustaqil monitor, joriy offer/reviewer/asset, capacity va sale readiness, quota/cap, provider spending limit read-back, handback custodian va operator ACK. Biror readiness yozuvi endi to‘g‘ri bo‘lmasa owner yoki javobgar rol egasi `/readiness withdraw` qiladi va yangi dalil bilan qayta tasdiqlaydi. Post-restore AT ro‘yxati — §8.5.
5. **Owner resume:** start `killed`; `shadow`+L0 faqat reconcile’dan keyin owner qadami bilan. Resume darajasi `min(snapshot_mode, off-host control journal’idagi oxirgi mode, L1_approve_each)` — journal faqat control-event ID, rejim va vaqtni saqlaydi, backup nusxasi emas (◇ P-33; `privacy-policy.yaml#off_host_flows`); journal o‘qilmasa barcha pipeline `L0_shadow` va owner har birini `control_resume` bilan alohida ochadi ([KILL_SWITCH §4.1](KILL_SWITCH.md)); bu qaytishlar gate emas. Stsenariy (d) da snapshot ham, `control_events` ham yo‘q: barcha pipeline `L0_shadow` dan boshlanadi va har capability o‘z gate’idan yangi dalil bilan qayta o‘tadi (Q55). Muddati o‘tgan approval tirilmaydi; release qilingan entity qayta takeover’siz ochilmaydi; B kill’dan keyin reklama o‘zi yoqilmaydi. Operatsion va biznes custody responderga qayta topshiriladi; o‘lchangan RTO va muammolar AAR’ga.

### 5.4 Stsenariy (e): ruxsatsiz kirish belgisi, PC joyida

Disklar shifrlanmagan (Q54), shuning uchun belgi topilganda ulardagi data va sirlar sizgan, holat esa o‘zgartirilgan bo‘lishi mumkin deb olinadi: odamlar va rollar, flag’lar, approval’lar, readiness imzolari, trust darajalari, ledger’lar va snapshot’lar ham. `MANIFEST` sha256’ini ham shu odam qayta hisoblay oladi, shuning uchun disklarni PC ichida tekshirib ishonchli deb bo‘lmaydi. Natija: PC joyida bo‘lsa ham operatsion holat stsenariy (d) dagidek quriladi va tekshirilgan disklardagi ma’lumot production’ga **tiklanmaydi** (◇ P-32). Barcha qadamlarni owner bajaradi (Q52):

1. **Izolyatsiya va fence.** INC-26; PC’ning tarmoq kabeli uzilgan, PC production’da yuklanmaydi. Writer fence’ning 1–3-qadamlari (§5) va to‘liq rotatsiya (§7) owner qurilmasidan.
2. **Apparat.** Owner qutining ichi, kabel va portlarni begona qurilma (USB qurilma, klaviatura va kabel orasidagi qurilma, qo‘shimcha karta) uchun ko‘zdan kechiradi; BIOS’ni zavod sozlamasiga qaytaradi, ona plata vendor’i saytidan olingan rasmiy firmware’ni qayta yozadi va HG-F0-01 sozlamalarini qayta qo‘yadi; yangi plomba (F0-AT-22). Begona qurilma topilsa yoki shubha qolsa — shu apparat ishlatilmaydi, qolgan qadamlar yangi PC’da (§5.1).
3. **Ixtiyoriy forensik nusxa — faqat PC ichida.** Owner USB’dagi Ubuntu Server o‘rnatuvchisini tarmoqsiz yuklaydi (BIOS paroli bilan bir martalik USB yuklash). O‘rnatuvchi shell’ida (Help → Enter shell) eski massiv faqat o‘qish uchun ishlatiladi: `cat /proc/mdstat` — o‘rnatuvchi uni o‘zi yig‘gan bo‘lsa `mdadm --readonly /dev/mdX`, aks holda `mdadm --assemble --readonly --scan`; fayl tizimi `ro,noload,noexec,nodev,nosuid` bilan mount qilinadi (`noload` — journal qayta yozilmaydi); tanlangan snapshot’ning `amt` dump’i va `MANIFEST`i hamda `/var/log/amt` o‘rnatuvchining RAM’idagi `/run/amt-forensic` (tmpfs) ga ko‘chiriladi. Sig‘masa yoki owner kerak demasa nusxa olinmaydi. Tashqi media (USB disk, boshqa kompyuter, bulut) ishlatilmaydi — bu AMT PC’dan chiqqan backup nusxasi bo‘lardi (Q55).
4. **Qayta o‘rnatish.** Massiv to‘xtatiladi (`mdadm --stop`), keyin [F0_Server](../05_Build_Phases/F0_Server.md) Appendix A dagidek ikkala disk tozalanib RAID1 va ikkala ESP bilan o‘rnatiladi. Forensik nusxa olingan bo‘lsa, o‘rnatish tugagach va "Reboot" dan oldin o‘rnatuvchi shell’ida u yangi tizimga ko‘chiriladi — `/target/var/lib/amt-forensic/` (root `0700`) — va `sha256sum` bilan solishtiriladi; RAM’dagi nusxa reboot bilan yo‘qoladi.
5. **Qayta qurish.** F2 live intake’dan oldin — F0 `build` rejimida; F2 dan keyin — `00-owner-bootstrap.sh --rebuild` va §5.1 checklist’ining 2–8-qadamlari (yangi PC o‘rniga shu apparat): sirlar va yangi server age kaliti, imzolangan tag’dan root skriptlari, manbalardan qayta qurish (§5.1 7-qadam, uch qoida), odamlar va rollar, approval’lar va readiness yangi dalil bilan qayta yopiladi (§5.1 8-qadam); keyin §5.3.
6. **Forensik tahlil (faqat AAR uchun).** Forensik nusxa production bazasiga hech qachon yuklanmaydi va undan hech narsa production’ga ko‘chirilmaydi. Dump hech qachon PostgreSQL serveriga tiklanmaydi: PostgreSQL hujjatiga ko‘ra dump tiklanganda uning muallifi tanlagan kod bajariladi, bu dump’ni esa begona odam o‘zgartirgan bo‘lishi mumkin. U faqat matn sifatida o‘qiladi — `pg_restore --list <dump>` va `pg_restore -f - -a -n amt -t audit_log -t people -t roles <dump>` (serverga ulanmaydi, hech narsa bajarilmaydi); audit zanjiri hash’lari shu matndan skript bilan qayta hisoblanadi: off-host heartbeat qayd etgan seq’dagi hash monitor saqlagan qiymat bilan, odamlar va rollar esa GitHub’dagi `roles.yaml` eksporti bilan solishtiriladi; natija va farqlar AAR’ga yoziladi. AAR yopilgach owner nusxani o‘chiradi.

## 6. Qulflanib qolish yoki kalit falokati

### 7.1 Writer fence va Tailscale qayta autentifikatsiyasi buyruqlari

Cloudflare qadamlari owner qurilmasida (AMT PC’da emas). "Cloudflare Tunnel Write" huquqli token owner’da qoladi va buyruq qatoriga yozilmaydi — sarlavha faylidan o‘qiladi:

```bash
# owner qurilmasida; ~/.cf-tunnel-write.hdr (0600) ichida bitta qator: "Authorization: Bearer <Cloudflare Tunnel Write token>"
CF="https://api.cloudflare.com/client/v4/accounts/<account_id>/cfd_tunnel/<tunnel_id>"
# (2) Zero Trust dashboard: tunnel -> "Rotate token"; yangi token sops'ga (TUNNEL_TOKEN)

curl -sS -X DELETE -H @"$HOME/.cf-tunnel-write.hdr" "$CF/connections"
# (5) yangi host cloudflared'ni yangi token bilan ishga tushirgach: ro'yxatda faqat uning connector'i bo'lishi shart
curl -sS -H @"$HOME/.cf-tunnel-write.hdr" "$CF/connections"
```

Tailscale qayta autentifikatsiyasi AMT PC’da root sifatida, lokal konsoldan (eski tugun admin konsolda olib tashlangach Tailscale orqali SSH ishlamaydi). Flag’lar run’lar orasida saqlanmaydi, shuning uchun har safar to‘liq to‘plam ([F0_Server](../05_Build_Phases/F0_Server.md) Appendix A) va `--force-reauth`; auth key buyruq qatorida emas, tmpfs’dagi faylda. ### 8.1 Restore tekshiruvi (`restore_check`, WF-O03)

AMT PC’da, `restore_test` muhitida: production klasteri bilan kesishmaydigan vaqtinchalik alohida klaster (`127.0.0.1:5433`), hech bir servis grant’i yo‘q ([environments.yaml](../09_Config_Templates/environments.yaml)); job, credential va egress yo‘q. Uni kunlik 04:30 muddat tekshiruvi (`restore_check`) `recovery.restore_check` dalili P25D yoshga yetganda ishga tushiradi (§3).

```bash
set -euo pipefail
SNAP=/var/backups/amt/<YYYY-MM-DDTHHMMZ>-nightly   # oxirgi tugallangan va tekshirilgan snapshot katalogi
sudo ls -l "$SNAP"                           # MANIFEST va artefaktlar: yoshi va hajmi
# MANIFEST'dagi har artefakt sha256'i qayta hisoblanib solishtiriladi (buyruq F0 manifest'ida [T])
PGV=16                                       # PostgreSQL major versiyasi (infra/VERSIONS.lock.md)
sudo pg_createcluster "$PGV" restore_test -p 5433 --start-conf=manual --start   # vaqtinchalik alohida klaster, faqat localhost:5433; boot'da o'zi ishga tushmaydi
trap 'sudo pg_dropcluster --stop "$PGV" restore_test' EXIT                      # xato bo'lsa ham klaster qolmaydi
sudo -u postgres createdb -p 5433 amt_restore_test
sudo cat "$SNAP/amt.dump" | sudo -u postgres pg_restore -p 5433 --no-owner --no-privileges -d amt_restore_test
sudo -u postgres psql -p 5433 -d amt_restore_test -c "select count(*) from amt.change_set_items;"
# count/checksum MANIFEST bilan solishtiriladi; natija va vaqt build/ops/restore-checks.md ga
```

### 8.3 Bitta DB’ni joyida tiklash (masalan, buzilgan migration)

Bu incident/rollback — maintenance hold emas; kill/resume qoidalari amal qiladi.

1. Owner qarori; owner `/pause_all` A yoki SSH `amt-kill --mode ai_only`.
2. Ta’sirlangan unitlarni to‘xtatish, masalan `sudo systemctl stop amt-gateway.service amt-executor.service amt-sync.service amt-workflow.service` (Paperclip DB uchun `paperclip.service` va barcha agent run’lari).
3. Eski DB o‘chirilmaydi, nomi almashtiriladi (oldin `df -h` bilan joy tekshiriladi): `sudo -u postgres psql -c "ALTER DATABASE amt RENAME TO amt_broken_<YYYYMMDD>;"`.
4. `sudo -u postgres createdb -O amt_migrator amt` → lokal snapshot’dan `pg_restore` (`sudo cat <snapshot>/amt.dump | sudo -u postgres pg_restore …`; upgrade’dan keyin — `amt-backup --pre-upgrade` snapshot’i) → grantlar migration orqali qayta qo‘llanadi ([DATA_MODEL §2](../03_Architecture/DATA_MODEL.md)) → constraint/count/hash.
5. Servislar tartib bilan yoqiladi, har biri ACK; tekshiruv per-service UID bilan, masalan `sudo -u amt-sync sync-worker --job tracking-health` (F2-AT-14).
6. Snapshotdan keyingi davr reconcile qilinadi: intake receipt’lar (landing custody va AMT ingest), `uncertain` attempt’lar, outbox, quota rezervlari, rol/policy revision’lari; `amt` tiklansa Paperclip proyeksiyasi `amt` workflow ledger’idan qayta sinxronlanadi; tashqi effekt replay qilinmaydi.
7. Tegishli faza AT’lari → owner resume ([KILL_SWITCH §4](KILL_SWITCH.md)) → AAR.

Paperclip upgrade’dan keyingi rollback ham shu yo‘l bilan, upgrade oldidan olingan lokal snapshot’dan: migration orqaga qaytmaydi, faqat restore ([UPGRADE §3](UPGRADE.md)).

### 8.4 Yangi PC uchun qo‘shimcha owner amallari (owner qurilmasida)

Recipient almashtirish, `sops updatekeys` va `sops rotate -i` owner qurilmasida bajariladi: owner age private kaliti AMT PC’ga hech qachon tushmaydi, AMT PC faqat yangi server kalitining public qismini beradi.

```bash
# owner qurilmasida (AMT PC'da emas): owner age kaliti qog'oz/QR nusxasidan tiklangach (Q56) yangi server recipient .sops.yaml ga qo'shilgan, eskisi olib tashlangan
set -euo pipefail
for f in secrets/*.sops.yaml; do
  sops updatekeys -y "$f"   # recipient ro'yxati (data key o'zgarmaydi)
  sops rotate -i "$f"       # yangi data key (sops >= 3.9; eskisida: sops -r -i); har buyruq alohida qatorda, xato skriptni to'xtatadi
done
# faqat shundan KEYIN yangi credential qiymatlari yoziladi (writer fence'dagi yangi TUNNEL_TOKEN ham)
```

Recipient olib tashlanganda (masalan o‘g‘irlangan server kaliti) `sops updatekeys` yolg‘iz yetmaydi: eski fayl (o‘g‘irlangan disk yoki git tarixi) va eski kalit bilan eski data key ochiladi va u bilan keyingi qiymatlar ham o‘qiladi. Shuning uchun har `secrets/*.sops.yaml` da yangi qiymat yozishdan oldin `sops rotate -i`. **Sinov** (sinov faylida va bir martalik sinov age kaliti bilan): sinov kaliti recipient bo‘lgan fayl nusxasi saqlanadi → kalit recipient’lardan olib tashlanadi, `sops rotate -i` → yangi sinov qiymati yoziladi → eski nusxadagi `sops` metadata bloki bilan yangi shifrlangan qiymatni sinov kaliti orqali ochish urinishi (`sops -d --ignore-mac`) rad etiladi. Faqat `updatekeys` bo‘lsa bu urinish o‘tardi; natija `build/ops/restore-checks.md` ga.

Tailscale admin’da eski tugun olib tashlanadi, yangi tugunning key expiry’si o‘chiriladi (HG-F0-04); Cloudflare’da writer fence’ning besh qadami (§5, buyruqlar §7.1) — token aylantiriladi, barcha mavjud ulanishlar uziladi, yangi token sops’ga yoziladi (HG-F0-02) va connector ro‘yxatida faqat yangi host qoladi; GitHub’da eski builder deploy key’lari o‘chiriladi va yangilari qo‘shiladi ([F0_Server](../05_Build_Phases/F0_Server.md) Appendix A); owner claude.ai’da eski builder Claude Code sessiyasini chiqaradi; eski host kalitlari hech qayerda qolmaydi.
